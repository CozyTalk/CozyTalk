## HIGH

### H-1 — `users` collection readable by any signed-in user, including email

**File:** `firestore.rules:41`

```
allow read: if isSignedIn();
```

Any authenticated user — including anonymous sign-ins — can query the entire `users` collection. The `users` docs contain `email` for email-registered users, plus `interest`, `thoughts`, `displayName`, `photoUrl`. For a privacy-by-design app that anonymises strangers, this exposes real email addresses to anyone who creates an anonymous account.

`friends_datasource.dart:46` (`watchAllUsers()`) does a full unbounded collection read, meaning all profiles (including email) stream to every authenticated client.

**Fix:** Remove `email` from Firestore storage entirely — it is never read from Firestore (all datasources read email from `FirebaseAuth`, not Firestore). Remove from `auth_datasource.dart` write calls, and from the Firestore `create`/`update` allowlists in `firestore.rules`.

---

### H-2 — `friendships` rule allows creating friendship without prior accepted friend request

**File:** `firestore.rules:175-182`

```
allow create: if isSignedIn()
  && request.auth.uid in request.resource.data.users
  // NO check that a matching friend_requests doc with status='accepted' exists
```

Any user can write a `friendships` doc directly, bypassing the friend-request flow. A malicious user sets `users: [self, victim]`, and the victim immediately sees the unsolicited "friendship" in their stream and can receive messages.

**Fix:** Split `acceptFriendRequest` batch write into two sequential writes (request update first, friendship create second). Add a Firestore rule cross-reference that verifies an accepted `friend_requests` doc exists before allowing the friendship to be created.

---

### H-3 — Proto-session key derivation mismatch: report chat logs are always unreadable

**Client:** `chat_datasource.dart:240`
```dart
final hash = await Sha256().hash(utf8.encode('cozytalk-proto-v1:$sessionId'));
```

**Server:** `reportSession.ts:57-58`
```typescript
function _deriveProtoKey(sessionId: string): string {
  return createHash("sha256").update(sessionId).digest("hex");
}
```

Client prefixes input with `'cozytalk-proto-v1:'`; server does not. Derived keys never match. When `reportSession` processes a proto-session, `_decryptMessage` silently returns `null` for every message — all proto-session reports have `text: null` for all entries, making moderation impossible.

**Fix:** In `reportSession.ts`, align the derivation:
```typescript
function _deriveProtoKey(sessionId: string): string {
  return createHash("sha256")
    .update(`cozytalk-proto-v1:${sessionId}`, "utf8")
    .digest("hex");
}
```

## MEDIUM

### M-1 — `typing` and `presence` RTDB paths readable by any authenticated user

**File:** `database.rules.json:17-18, 58-60`

```json
"typing":   { "$room_id": { ".read": "auth != null" } }
"presence": { "$room_id": { ".read": "auth != null" } }
```

Any authenticated user (including anonymous) can listen to typing indicators and presence for **every room**, regardless of membership. This leaks which rooms are active, how many users are in them, and their display names.

**Fix:** Restrict read to room members:
```json
".read": "auth != null && root.child('rooms').child($room_id).child('members').child(auth.uid).exists()"
```

---

### M-2 — `user_status` RTDB path readable by any authenticated user

**File:** `database.rules.json:33`

```json
"user_status": { "$uid": { ".read": "auth != null" } }
```

Any authenticated user can read any user's status (`online`, `in_room`), `roomId`, and `roomMode`. Combined with typing/presence, this enables activity-tracking of any user by any stranger.

**Fix:** Restrict to owner: `"auth != null && auth.uid == $uid"`.

---

### M-3 — `contextImageUrls` in `reportSession` not validated as Storage URLs

**File:** `reportSession.ts:127-134`

`contextImageUrls` are validated as strings but not as Firebase Storage URLs. Arbitrary URLs could be stored in admin-only report documents. If the admin console renders these, it becomes a phishing/tracking vector against admins.

**Fix:** Validate URLs start with `"https://firebasestorage.googleapis.com/"` before accepting them.

## LOW / INFO

### L-1 — Firebase web API key hardcoded in committed test file

**File:** `functions/src/matchmaking/__tests__/testProdVertexAI.ts:17`

```typescript
const API_KEY = "AIzaSyAhEm1tJRomLx7ErcaHDYSlnyrpchgmro8";
```

Same public key as in `firebase_options.dart`. Not exploitable for data access (security comes from rules). Makes it easier to automate quota-exhaustion or auth-endpoint spam.

**Fix:** Use `process.env.FIREBASE_WEB_API_KEY ?? "..."` with a fallback.

---

### L-2 — Proto-session messages write `expiresAt: FieldValue.serverTimestamp()` (immediate TTL)

**File:** `chat_datasource.dart:149`

Proto-session client-side writes set `expiresAt` to the current timestamp instead of a 3-day future timestamp. If the Firestore TTL policy is active, these messages are immediately TTL-eligible.

**Fix:** Set `expiresAt` to `DateTime.now() + 3 days` using `Timestamp.fromMillisecondsSinceEpoch`.

---

### L-3 — Admin console ban/resolve actions are mock-only with no Firebase enforcement

**Files:** All `screens/admin_*.dart` files

All data is hardcoded in-memory. Ban and resolve actions have zero effect on Firebase Auth or Firestore. If inadvertently used in production, no user would actually be restricted.

**Fix:** Add `assert(false, ...)` guard in `AdminConsoleScreen.build()` to make the prototype status unmistakable.

---

### L-4 — `friendships` delete doesn't clean up `friend_messages` subcollection

**File:** `firestore.rules:180-182`

When a friendship is deleted, the `friend_messages/{id}/messages` subcollection orphans in Firestore. Access is naturally blocked (the participant check on a deleted doc returns false), but data persists consuming storage indefinitely.

**Fix:** Add a Firestore `onDocumentDeleted` trigger on `friendships/{id}` that calls `deleteSubcollection` on the messages subcollection.

---

### L-5 — User interest text stored in SharedPreferences (plaintext)

**File:** `matchmaking_provider.dart:145`

Interest text (`"I love hiking"`) is persisted to SharedPreferences. App-sandbox protected on Android, but accessible on rooted devices. Low sensitivity — no credentials involved.

**Fix:** Acceptable as-is for a prototype. Use `flutter_secure_storage` if richer profile data is added later.

---

### L-6 — `photoUrl` written to RTDB typing node without format validation

**File:** `chat_datasource.dart:176` + `database.rules.json:20-22`

The RTDB typing rule validates `isTyping` and `displayName` but has no rule on extra child fields, allowing arbitrary data to be stored under a user's typing node.

**Fix:** Add explicit per-field rules and `"$other": { ".validate": false }` to the typing `$uid` node. Retain `photoUrl` as an explicitly allowed optional field.

## Privacy Note — `friend_messages` stored unencrypted

Friend messages are stored as plaintext in `friend_messages/{id}/messages/`. Acknowledged as "permanent, no TTL, no encryption (prototype)" in CLAUDE.md. This is a privacy regression vs. the ephemeral encrypted chat flow and must be addressed before the friends feature exits prototype status.
