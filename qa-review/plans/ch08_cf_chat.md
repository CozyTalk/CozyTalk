## Checks to Perform

### 8.1 `sendMessage.ts`
- [ ] Auth check: rejects unauthenticated callers.
- [ ] Validates `sessionId` and `message` params are non-empty strings.
- [ ] Validates `message` length ≤ some reasonable limit (prevent unbounded plaintext before encryption).
- [ ] AES-256-GCM encryption:
  - Generates a unique random IV per message (not reused).
  - IV is 12 bytes (96 bits) — standard for GCM.
  - Auth tag is generated and stored.
  - Encryption key sourced from `rooms/{sessionId}.encryptionKey` (not hardcoded, not from client).
- [ ] Writes to `chat_rooms/{sessionId}/messages/{messageId}`:
  - `senderId` set to authenticated UID (not from client payload).
  - `displayName` sourced from Firestore `users/{uid}.displayName` (not from client payload — prevents spoofing).
  - `encryptedText`, `iv`, `authTag` stored as base64 strings.
  - `timestamp: FieldValue.serverTimestamp()`.
  - `expiresAt: now + 3 days` (TTL policy).
  - `flagged: false` initially.
- [ ] `flagged` field: is it set based on content scanning or just default false?
- [ ] Message ID: auto-generated by Firestore, not client-provided.
- [ ] Rate limiting: is there any protection against message flooding? (flag if not — MEDIUM risk).
- [ ] JSDoc with `@param` and `@return`.

### 8.2 `endSession.ts`
- [ ] Auth check.
- [ ] Validates `sessionId`.
- [ ] Verifies caller is a participant of the session (`rooms/{sessionId}.users` includes caller UID).
- [ ] Archives encryption key to `session_keys/{sessionId}`:
  - `sessionId`, `encryptionKey`, `users`, `createdAt`, `expiresAt`, `flagged`.
- [ ] Destroys RTDB `rooms/{roomId}/members/{uid}` data.
- [ ] Destroys RTDB `typing/{sessionId}` and `presence/{sessionId}` data.
- [ ] Does NOT destroy `chat_rooms/{sessionId}/messages` — those are TTL-expired, not immediately deleted.
- [ ] Updates `rooms/{sessionId}.status` to `expired`.
- [ ] Deletes `active_sessions/{sessionId}` (legacy proto-session cleanup).
- [ ] Is this operation atomic? What happens if it partially fails (e.g., key archived but RTDB not cleaned)?
- [ ] JSDoc.

### 8.3 `reportSession.ts`
- [ ] Auth check.
- [ ] Validates `sessionId`, `reportedUid`, `reason`, `description`.
- [ ] Verifies reporter is a participant of the session.
- [ ] Reads and retains `chat_rooms/{sessionId}/messages` (the chat log) into `reports/{reportId}.chatLog`.
- [ ] Writes to `reports/{reportId}`:
  - `reason`, `description`, `chatLog`, `status: 'pending'`.
  - `reporterId` from authenticated UID (not payload).
  - `reportedUid` validated to be the OTHER participant (not self-report).
  - `timestamp: FieldValue.serverTimestamp()`.
- [ ] After writing report: **does NOT destroy the chat log** — per CLAUDE.md, log is retained for moderation.
- [ ] Does the normal `endSession` cleanup still happen after report? Or is session kept alive?
- [ ] Prevention of duplicate reports for same session (idempotency).
- [ ] JSDoc.

### 8.4 `setTyping.ts`
- [ ] Per CLAUDE.md: client writes `typing/{roomId}/{uid}` directly via RTDB SDK — no CF needed.
- [ ] Confirm this file exists but is either: (a) not exported, or (b) completely empty/stub.
- [ ] If it IS exported: flag as inconsistency with documentation.
- [ ] If it doesn't exist: flag that the file was listed in directory tree — investigate.

### 8.5 `onProtoPresenceDeleted.ts` (RTDB Trigger)
- [ ] Triggered on proto-session presence deletion.
- [ ] Cleans up proto-session-related Firestore data (`active_sessions/{sessionId}`).
- [ ] Region: `us-central1` or `asia-southeast1`? Confirm correct region for RTDB trigger.
- [ ] Doesn't interfere with new-style `rooms/{roomId}` cleanup.
- [ ] JSDoc.

### 8.6 Encryption Key Security
- [ ] Encryption key for 1v1 sessions generated at room creation in `match1v1Users.ts`.
- [ ] Key is stored in `rooms/{roomId}.encryptionKey` in Firestore.
- [ ] Firestore security rules: does the key field leak to clients who can read `rooms/{roomId}`?
  - Cross-reference with Chapter 9 (security rules check).
  - If clients can read the encryption key, AES-256-GCM provides NO security over plaintext.
- [ ] Key archived to `session_keys/{sessionId}` by `endSession` — confirm `session_keys` is write-locked to CFs only.

### 8.7 Privacy by Design Verification
- [ ] `endSession` destroys RTDB data immediately — not queued/delayed.
- [ ] `chat_rooms/{sessionId}/messages` TTL policy set to 3 days — confirm `expiresAt` is always set.
- [ ] `reportSession` is the ONLY path that retains chat log — no other CF writes to a persistent chat log store.
- [ ] Reported sessions: does the session end after report? Or does it stay active for the remaining duration?

### 8.8 TypeScript/ESLint Compliance
- [ ] All chat CFs: no implicit `any`.
- [ ] Structured errors via `HttpsError`.
- [ ] Double quotes, 2-space indent, trailing commas, semicolons.
- [ ] JSDoc on all `function` declarations.
- [ ] `npm run lint` passes clean for `chat/` directory.

### 8.9 Cross-Chat Security Checks
- [ ] `displayName` in messages: sourced from Firestore (server-authoritative), not client payload.
- [ ] `senderId` in messages: always set from authenticated UID (not client payload).
- [ ] A user cannot read another user's session messages (covered by Firestore rules — cross-ref Ch09).
- [ ] `encryptedText` max 12KB enforced in `sendMessage` (per Firestore rules spec in CLAUDE.md).
- [ ] `displayName` max 200 chars enforced in `sendMessage`.
